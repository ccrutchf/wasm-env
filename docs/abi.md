# wasm-env native ABI (`wasm64-linux-musl`), version 0

This document defines what a wasm-env program is: the contract between a WebAssembly module and the wasm-env runtime. Recompiled software targets it through our toolchain. Translated binaries (see PLAN.md) will target it too. Status: draft (M0, extended in M1 with processes); everything may change until M3.

The guiding rule: **be Linux**. Where Linux already defines something (syscall numbers, struct layouts, errno values, the initial process stack), we use the Linux definition, specifically the one for **arm64**, which uses the modern generic syscall table and 64-bit struct layouts. A port of existing software should see nothing unusual except the CPU.

## Module shape

A wasm-env program is a single core WebAssembly module (not a component).

| Item | Kind | Requirement |
|---|---|---|
| `memory` | exported memory | memory64 (64-bit addresses), the program's only memory |
| `_start` | exported function `(i64) -> ()` | Entry point; takes a pointer to the initial process stack (see below) |
| `__stack_pointer` | exported mutable `i64` global | The shadow-stack pointer (LLVM's C stack in linear memory) |
| `__heap_base` | exported `i64` global | First address after static data and the stack; the runtime's memory map starts here |
| `linux.syscall` | imported function `(i64 × 7) -> i64` | The only way to reach the system (see below) |

A module may import nothing else. The runtime rejects modules that don't match.

### WebAssembly features

Programs may use: memory64, bulk memory, mutable globals, sign extension, non-trapping float-to-int, multi-value, reference types, SIMD (128-bit), exception handling (the standard `exnref` form, used for `setjmp`/`longjmp` and C++ exceptions) and tail calls.

Not allowed in version 0: threads, shared memory, multiple memories. The runtime's arm64 translator produces modules of a threaded shape instead (see "Threads").

## System calls

```
(import "linux" "syscall" (func (param $nr i64) (param i64 i64 i64 i64 i64 i64) (result i64)))
```

- `$nr` is a Linux syscall number from the **generic table** (`include/uapi/asm-generic/unistd.h`, as used by arm64). For example, `openat` is 56, `read` is 63, `write` is 64, `exit_group` is 94. Legacy calls that only exist on older architectures (`open`, `stat`, `fork`) don't exist here, just as on arm64.
- Up to six arguments, each an `i64`. Unused arguments are ignored. Pointers are addresses in the program's memory.
- The result is the raw kernel return value: a non-negative result on success, or `-errno` (−4095 to −1) on failure. Errno values are Linux's generic values. libc turns this into `errno`.
- Structures passed through pointers use arm64 Linux layouts (LP64: `long` and pointers are 8 bytes; `struct stat` is the generic 128-byte layout).
- A syscall the runtime doesn't implement returns `-ENOSYS` (−38). It never traps.
- The runtime validates every pointer and length against the program's memory; a bad pointer returns `-EFAULT`.
- Event loops (libuv's, Node.js's): `eventfd2`, `epoll_create1`, `epoll_ctl` and `epoll_pwait`/`epoll_pwait2` (level-triggered: `EPOLLET` behaves like it, which suits loops that read until `EAGAIN`, except on files, directories and devices, whose readiness never changes: those report once, until `EPOLL_CTL_MOD`; `EPOLLONESHOT` is honoured), and `socketpair` for `AF_UNIX` (host socket pairs; see "Networking").
- File watching: `inotify_init1`, `inotify_add_watch`, `inotify_rm_watch` are the runtime's, on every host: a watch on a file under the root, or on a directory and its entries, with the host's file-watching service behind it (inotify on Linux, FSEvents on macOS, `ReadDirectoryChangesW` on Windows). Events are Linux's `struct inotify_event`s (names relative to the watched directory; renames paired by cookie), and arrive as the host notices changes, a moment after them rather than with the call that made them. `prctl` accepts setting a thread's name, the parent-death signal, dumpability and no-new-privileges, and reports the process dumpable; `fadvise64` is accepted; `fallocate` is the host file's.

This mirrors the arm64 `svc #0` convention, so translated arm64 binaries can map their syscalls onto this import one-to-one, and x86-64 translation only needs a number-mapping table.

## Process startup

Linux starts a process with argc, argv, the environment and the auxiliary vector laid out at the top of its stack. wasm-env does the same, in the program's memory:

1. The runtime instantiates the module and reads `__stack_pointer`.
2. It writes the initial process stack just below that address, 16-byte aligned, in exactly the Linux layout:

   ```
   sp →  argc
         argv[0] … argv[argc-1], NULL
         envp[0] … envp[n-1], NULL
         auxv: (type, value) pairs …, (AT_NULL, 0)
         … padding, 16 random bytes (AT_RANDOM), argument and environment strings
   ```

   Every slot is 8 bytes.
3. It sets `__stack_pointer` to `sp` (so the C stack continues below the block) and calls `_start(sp)`.

`_start` is libc's (`crt1.o`), and it hands `sp` to `__libc_start_main` exactly as on Linux.

Auxiliary vector entries provided: `AT_PAGESZ` (4096), `AT_RANDOM`, `AT_UID`, `AT_EUID`, `AT_GID`, `AT_EGID`, `AT_SECURE` (0), `AT_HWCAP` (0), `AT_EXECFN`. There is no `AT_PHDR`, because a WebAssembly module has no ELF program headers.

The program exits by calling `exit_group`. If `_start` returns, the runtime treats it as `exit_group(0)`. A trap (for example, an out-of-bounds access below the masking limit) terminates the process as if by `SIGSEGV`: exit status 139 in the shell.

## Memory

- The program's memory is **masked memory64** (see PLAN.md, "Masked addressing"): up to 2^38 bytes (256 GB). Addresses above that wrap; out-of-bounds addresses below it trap.
- Static data and the C stack sit below `__heap_base`, laid out by the linker. The default stack is 8 MB, like Linux.
- Above the break's region, the runtime manages the address space for `mmap`, in 4 KB pages, growing the WebAssembly memory as needed. Anonymous mappings come back zero-filled. `munmap` returns pages for reuse. An address hint is honoured, as on Linux, when that range is free: in the `mmap` region below its top, or in the break's region above the break (LuaJIT asks for code memory near its VM, within reach of direct branches); `brk` then can't grow into such a mapping.
- The program break starts at `__heap_base` and `brk` moves it within a 64 MB region (zero-filling what it exposes); a request beyond that returns the current break, which is how Linux reports failure, and allocators fall back to `mmap`. The `mmap` region begins above the break's.
- Page protections (`mprotect`) aren't enforced: WebAssembly can't, inside linear memory. `PROT_EXEC` marks where a program puts code it generates (see "Code generated at run time").
- A private file mapping (`MAP_PRIVATE`) is a copy of the file, read in on `mmap`. A shared one (`MAP_SHARED`, of a file or a memfd, or anonymous) is a host mapping of the file placed at the guest address inside the process's memory, so writes reach the file and other processes see them, a forked child included (it maps the same files); `msync` has nothing to do. `munmap`, or a new mapping over it, puts zeroed private memory back; `mremap` moves a whole shared mapping as one. (On Unix hosts, Linux and macOS. On Windows a shared file mapping is a copy, like a private one, recorded so the compositor reads graphical programs' buffers from it; processes don't share memory there yet.) `memfd_create` makes a host memfd on Linux, whose seals (`F_ADD_SEALS`, `F_GET_SEALS`) are the host's, elsewhere an unlinked temporary file, and on Windows a temporary file deleted when it's closed (no seals: `EINVAL`, as for a file without them); a file's inode is the host's, or on Windows (whose metadata has none) one made from its path, so different files' differ, as glibc's loader needs to tell libraries apart; `fallocate` is the host's on Linux, and elsewhere its plain form (making a file at least a size) by growing the file.

## Threads and thread-local storage

Programs built with the wasm-env toolchain (version 0) are single-threaded. `clone` with `CLONE_THREAD` returns `-ENOSYS`, so `pthread_create` fails cleanly. musl's thread pointer, which it uses for `errno` and its own bookkeeping, is an ordinary global variable in libc, set by `__set_thread_area`. There is no ELF TLS segment. C `_Thread_local` variables compile to ordinary globals, which is correct with one thread.

**Threads.** Translated (arm64) programs can have threads. Their modules have a different shape:

| Item | Kind | Requirement |
|---|---|---|
| `env.memory` | imported memory | shared, memory64, with a maximum (the runtime creates it) |
| `__wasm_init_tls` | exported function `(i64) -> ()` | Points this instance's thread-local block at the address given, and initializes it |
| `__tls_size`, `__tls_align` | exported `i64` globals | The thread-local block's size and alignment |
| `__wasm_env_thread_start` | exported function `(i64) -> ()` | Starts a new thread from a clone frame (below) |
| `wasm-env.image` | custom section | The guest image: pages the runtime maps into memory copy-on-write before instantiating (translator/src/link.rs, `add_image`) |

plus `_start`, `__stack_pointer`, `__heap_base` and `linux.syscall` as above. wasm-ld builds this shape with `--shared-memory --import-memory`: data is initialized by a start function that only the first instance runs.

Each guest thread is its own instance of the module on the shared memory, in its own wasmtime store, on its own host thread. The instance's thread-local block holds the thread's guest registers, its exclusive monitor and its dispatch cache, so translated code runs without any per-thread indirection other than `__tls_base`. At `clone(CLONE_THREAD | CLONE_VM | CLONE_SIGHAND, ...)` the support code writes a *clone frame*: the parent's registers, with x0 = 0, SP = the new stack, TPIDR_EL0 = the `tls` argument (with `CLONE_SETTLS`) and the address after the `svc` to resume at. It passes the frame's address to the runtime's `clone` as a sixth argument. The runtime allocates a tid, honours `CLONE_PARENT_SETTID`, `CLONE_CHILD_SETTID` and `CLONE_CHILD_CLEARTID`, instantiates the module again, gives the instance a thread-local block and a 64 KB C stack from the mmap region, and calls `__wasm_env_thread_start(frame)`. The new thread copies its registers and makes the wasm-env call `thread_started`; only then does `clone` return the tid to the parent, which may reuse the frame.

Atomics: load-acquire, store-release and the LSE atomics become WebAssembly atomics (sequentially consistent, so at least as strong as arm64 asks); `dmb`/`dsb` become `atomic.fence`. A load-exclusive records the value it read, and a store-exclusive is a compare-and-swap against that value, as QEMU does it (a store of the same value in between goes unnoticed). Ordinary loads and stores are ordinary WebAssembly accesses.

What threads share: memory, the descriptor table, the working directory, signal dispositions, the address space (`mmap`, `brk`), futexes and pending signals (a signal to the process is taken by a thread that doesn't block it, at its next syscall). Each thread has its own signal mask and alternate signal stack; the umask is per thread too, copied from the creating thread. `getpid` returns the process id; `gettid` the thread's (the first thread's is the pid). `sched_getaffinity`, `/proc/cpuinfo` and `/sys/devices/system/cpu/{online,possible,present}` report the host's CPUs.

`futex` supports `FUTEX_WAIT`, `FUTEX_WAKE`, `FUTEX_WAIT_BITSET`, `FUTEX_WAKE_BITSET`, `FUTEX_REQUEUE` and `FUTEX_CMP_REQUEUE` (private or not: processes don't share memory); a wait returns `-EINTR` when a signal arrives or the process is ending. `exit` ends the calling thread (clearing its tid word and waking a waiter on it, for `pthread_join`); when the last thread exits, the process exits with its status. `exit_group`, a fatal signal, a trap in any thread or `execve` end the whole process: the other threads stop at their next syscall, and blocking calls return early. (A thread that never makes another syscall keeps running until the environment exits.)

## Libraries

A translated program's shared libraries are **modules of their own**, translated once per library and shared by every program that uses it, as on Linux. (`WASM_ENV_MONOLITHIC=1` translates a program together with its libraries in one module instead, the earlier way.)

- The **main module** is the executable alone, with the translator's support code. It exports, besides the items under "Threads": `__indirect_function_table`, the guest-state global `__wasm_env_state`, the support code's entry points (`dispatch`, `__wasm_env_svc`, `__wasm_env_svc_at`, `__wasm_env_fp_flags`, `__wasm_env_fatal`, `__wasm_env_bad_target`, `__wasm_env_crc32`, `__wasm_env_counter`) and the module directory (`__wasm_env_modules`, `__wasm_env_module_count`, `__wasm_env_modules_added`, and the code epoch `__wasm_env_code_epoch`, see "Code generated at run time"), and its region table (`dispatch_addrs`, `dispatch_fns`, `dispatch_count`, see "Blocks a translation missed").
- A **library module** is a position-independent side module in wasm-ld's dynamic-linking convention (`dylink.0`; `--experimental-pic -shared`). It imports the shared memory, the function table, `__stack_pointer`, `__memory_base`, `__table_base`, `__wasm_env_state` and the support code's entry points from `env`, and a `GOT.func` global per function whose address its data holds (its region functions). It exports its region table (`dispatch_addrs`, `dispatch_fns`, `dispatch_count`, relative to `__memory_base`), and a custom section `wasm-env.library` records the guest range it was translated for (two u64s, start and end).

**Guest state** is a block per thread (`struct guest_state` in the support code: registers, flags, the exclusive monitor and the dispatch cache), at the address in the WebAssembly global `__wasm_env_state`, which every module of a thread shares. Each region function reads it once.

**Addresses.** Each library is translated for a fixed guest range, which the runtime keeps from one translation to the next in its cache (`library-bases`), from 64 GB upward: every library has its own range, so any set of them fits in one process. The executable keeps its own addresses.

**Loading.** At start, the runtime loads the program's dynamic linker (PT_INTERP) as the kernel would: it maps its segments at its range and loads its module, and adds `AT_BASE` and a wasm-env entry `0x7700` (where to start: the dynamic linker's entry) to the auxiliary vector. When the dynamic linker then maps a library, the support code asks the runtime with the wasm-env call `load_library(fd, range)`: if the file is an arm64 shared object, the runtime translates it if it hasn't yet, loads its module and writes its guest range to `range` (else `-ENOEXEC`, and the file is mapped as data). The support code places the dynamic linker's mappings of the library in that range, as with the monolithic translation's prelinked bases. A library opened again after a `dlclose` (which unmaps nothing) is the same library: its range, and glibc's reservation in it, are recorded once, so a program loading and unloading one in a loop (SDL does libudev, polling for devices) doesn't fill the support code's tables; and the file the dynamic linker opened, whose reservation is the library's, is remembered per thread, so other threads opening files meanwhile don't move it (`dlopen_loop` in tests/ubuntu.sh).

Loading a module into a process: the runtime allocates its data (`dylink.0`'s size and alignment) in the mmap region and its function-table slots after the main module's, instantiates it against the main instance's exports (filling each `GOT.func` global with its slot, and the slot with the exported function), runs `__wasm_apply_data_relocs` once, and adds an entry `{start, end, region addresses, region functions, count, generation}` to the module directory, in a free slot (one a retired module left, else the next; `__wasm_env_module_count` is the number of slots used), writing the range last, and increments `__wasm_env_modules_added`. `dispatch` searches the directory for addresses outside the main module. Each thread has instances of the modules in its own store, with the same placements; a thread that finds a module when more have been added than it has caught up with asks the runtime to catch up (the wasm-env call `sync_modules`), and a new thread instantiates all loaded modules before it starts. Libraries stay loaded until the process exits (`dlclose` unmaps nothing).

## Code generated at run time

A JIT (oneDNN's Xbyak, LuaJIT) writes machine code into memory and jumps to it. The runtime records the memory a program makes executable: an anonymous `mmap` with `PROT_EXEC`, a shared mapping of a file with it (a JIT that keeps W^X, as GStreamer's ORC does, writes its code through a second, writable mapping of the same file; libraries are private mappings; where shared mappings are copies, on Windows, what was written through the file's other mappings in the process is brought over before code is translated), or `mprotect` adding it. When control reaches an address no module covers, `dispatch` asks the runtime (the wasm-env call `translate_code(address)`) to translate the executable mapping holding it, as it is then, from that address: the translator's `--raw` input, code bytes at a base with the addresses it was entered at as block roots. Such code, and a page translated again (see "Blocks a translation missed"), is compiled straight from the lifter's IR to WebAssembly by the translator's own compiler (translator/src/wasmgen.rs), in the runtime's process (about a millisecond, where clang and wasm-ld take a tenth of a second or more), which makes the same side module; what it doesn't handle yet (vector arithmetic, some intrinsics; lane access, bitcasts between vectors and registers, and structure loads and stores, `ld3`'s `<24 x i8>` kept in two v128s and split by `i8x16.shuffle`, it does) goes to clang, at `-O1` (the program waits). The result is a module like a library's, added to the module directory the same way, covering only the whole pages its blocks occupy, and cached by bytes, base and roots (a JIT that chooses its addresses generates the same code run after run).

**Chaining.** A translation covers only the code reached from the address it was made for, following control flow within that address's page; it doesn't translate the page's other code again. Several modules may therefore cover a page, and `dispatch` takes the newest whose region table has the region. An address a module has no block for goes on to the older code: its region function's missed case tail-calls, through the table slot its import `prev.R_<region>` holds, the function of the same region in the next older live module, and the chain ends at a slot holding the support code's `__wasm_env_bad_target`, which translates that entry. A new module sharing a page with older code bumps the code epoch, so dispatch caches drop the older function. Modules sharing a page all keep that page's bytes, so a change to it retires them together. (What the direct compiler doesn't handle is compiled by clang, whose module doesn't chain: it takes the entries of the modules on its pages and replaces them.)


**Retiring.** A module keeps the bytes it was translated from. When the program makes memory executable again (a JIT that changes or adds code makes it writable first), modules there whose bytes changed are retired; unmapping or remapping memory retires its modules outright. Retiring empties the module's directory entry (the slot is reused) and increments `__wasm_env_code_epoch`; each thread clears its dispatch cache, which may name the old code, when it sees a new epoch (after a system call, and in `dispatch`). Code changed while it stays writable and executable, without an `mprotect`, is noticed the way the processor would: code written as data runs only after `ic ivau` over its cache lines and an `isb`, which a JIT does itself or through `__builtin___clear_cache`. The lifted `ic ivau` notes its line (in the support code), and the next `isb` has the runtime compare the translations of those lines with the bytes now (the wasm-env call `code_changed`), retiring those that differ; the `isb` also checks the code epoch, so it sees other threads' changes too.

## Blocks a translation missed

Discovery can't find every block: an interpreter may reach its handlers through a table it builds at run time, as LuaJIT's does. When control reaches an address its translation (the program's, or a library module's) has no block for, the support code asks the runtime with `translate_code(address, object, base)` (the object and base from the program's object list, or zero for a library module, which the runtime knows). The runtime records the address in the module's `.roots` file, so the next translation includes it as a block root, and translates that one page again right away: the translator's `--page` option, the object translated as before (same mode and base) with every root recorded so far, emitting only that page's region, whose jumps to other regions go through `dispatch`. The new module takes over the page's entry in the owner's region table (the main module exports its table: `dispatch_addrs`, `dispatch_fns`, `dispatch_count`), and is also added to the module directory, where `dispatch` finds it if the translation had no region on that page (`dispatch` searches past a module whose table lacks the region). An earlier patch of the page is retired, and the code epoch bumped either way. So the run goes on: a program whose translation misses blocks no longer stops at each one. Around a recorded address, discovery also takes the instruction after each unconditional branch or return as a block start, so one missed handler reveals its neighbours. (Not for a program translated together with its dynamic linker, whose image isn't one object's: that stops, and the next run translates the address.)

## `setjmp` and `longjmp`

The compiler rewrites `setjmp`/`longjmp` using WebAssembly exception handling (`-mllvm -wasm-enable-sjlj`): `longjmp` throws the C tag `__c_longjmp`, and functions that call `setjmp` catch it and check whether it's theirs. libc supplies the three helpers the compiler calls (`__wasm_setjmp`, `__wasm_setjmp_test`, `__wasm_longjmp`). Everything linked into a program must be compiled with the same flags.

## Processes

Processes are created with **`vfork` + `execve`**, which covers `posix_spawn`, `system`, `popen` and shells; translated programs can also `fork` (see "fork (translated programs)" below).

**vfork.** `clone(CLONE_VM | CLONE_VFORK | SIGCHLD, 0)` (no new stack) enters a *vfork child*:

1. The runtime allocates the child's pid and saves the parent's process state (descriptor table, working directory, umask, signal dispositions). The child continues **in the parent's memory, on the parent's call stack**, with its own copy of that state, exactly as a real vfork child shares its parent's memory.
2. When the child calls `execve` and it succeeds, the runtime starts the new program as the child's pid, restores the parent's state, and **returns the child's pid** (instead of not returning).
3. When the child calls `exit_group`, the runtime records the child's exit status, restores the parent's state, and **returns the child's pid**.
4. In both cases libc then `longjmp`s back to the `vfork` call site, where `vfork()` returns the pid to the parent.

`vfork` returns twice, so libc defines it as a macro around `setjmp` (see `toolchain/musl-overlay/src/process/wasm64/vfork.c`); the child must not return from the function that called `vfork`, the usual vfork rule. `clone` with any other flags returns `-ENOSYS`.

Translated (arm64) programs use the same protocol through the translator's support code, so their own libc's `vfork`, `posix_spawn` and `system` work: at the guest's `clone(CLONE_VM | CLONE_VFORK, stack)` the support code saves the guest registers and the address after the `svc`, and the child continues (on `stack` if one is given, as glibc's `posix_spawn` does). When the runtime returns the child's pid from its `execve` or `exit`, the support code restores the registers, puts the pid in x0 and resumes the parent after its `clone`.

**execve** accepts WebAssembly programs, `#!` scripts (up to four levels of interpreter) and arm64 ELF binaries, which the runtime translates on first use (with their dynamic linker and libraries from the environment) and caches. Other files fail with `-ENOEXEC`. Outside a vfork child, a successful `execve` replaces the running program; the pid, descriptors (minus close-on-exec ones), working directory, umask and ignored signals carry over.

**Process model.** Each process runs on its own host thread, all inside the environment's one host process. `wait4` supports the usual targets (-1, a pid, 0, -pgid) and `WNOHANG`, and reports standard Linux wait statuses. Pipes are in-runtime buffers of 64 KB; writing to a pipe without readers raises `SIGPIPE`.

**Signals.** `kill`, `tkill` and `tgkill` queue a signal for the process (a set of pending signals; threads share them); it's acted on at a syscall of one of its threads that doesn't block it (`rt_sigprocmask`, per thread, kept across exec), and blocking calls (`read` on a pipe, `wait4`, `nanosleep`, `futex`, `poll`) return `-EINTR` when one arrives that would do something. Default actions apply (terminate, or ignore for SIGCHLD, SIGCONT, SIGURG and SIGWINCH), `SIG_IGN` is honored, and a child's exit sends its parent SIGCHLD. The first program starts with the signals ignored that wasm-env was started with ignored (a shell's `trap ''`, `nohup`, a background job), as a program exec'd keeps them; not SIGPIPE, which Rust's startup ignores before the runtime can see the host's. **Handlers run in translated programs**: when a syscall returns with a signal to deliver, the runtime writes the handler's details into the thread's guest-state block (`struct signal_delivery`), and the support code does what the arm64 kernel does: it pushes a `struct rt_sigframe` (siginfo, and a ucontext with the registers, NZCV, the FP/SIMD record and the old mask) on the stack, or the `sigaltstack` for `SA_ONSTACK`, and enters the handler with x0 = the signal, x1 = &siginfo, x2 = &ucontext and x30 = the `sa_restorer` (`SA_RESTORER`), else an address `dispatch` takes as `rt_sigreturn` (for glibc, which relies on the kernel's vDSO trampoline). `rt_sigreturn` restores the state from the frame. `SA_NODEFER`, `SA_RESETHAND`, `sa_mask`, `rt_sigsuspend`, `rt_sigpending` and `setitimer`/`getitimer` (`ITIMER_REAL`, SIGALRM) work. Not yet: `SA_RESTART` (interrupted calls return `-EINTR`, which Python and most libraries retry), signals interrupting code between syscalls, and handlers in programs built with the toolchain (their handled signals are ignored).

**Devices.** The runtime provides `/dev/null`, `/dev/zero`, `/dev/random`, `/dev/urandom`, `/dev/stdin`, `/dev/stdout`, `/dev/stderr` and `/dev/fd/N`, whatever the root directory contains.
It also generates `/proc/cpuinfo`, `/sys/devices/system/cpu/{online,possible,present}` (the host's CPUs) and a directory per CPU with its `topology/` (each CPU a core of its own, in one package: what hwloc, and so pocl, reads), `/proc/meminfo` (the host's memory), `/proc/mounts`, `/proc/self/mounts`, `/etc/mtab` and `/proc/self/mountinfo` (the root, and `/proc`).

**Networking.** Sockets are the host's: a program reaches the network, and binds ports, as the host would. Supported: `AF_INET` and `AF_INET6` sockets, stream and datagram (`SOCK_NONBLOCK` and `SOCK_CLOEXEC` too); `connect` (a non-blocking one reports `-EINPROGRESS`, then its result through `SO_ERROR`), `bind`, `listen`, `accept`/`accept4`, `getsockname`, `getpeername`, `sendto`, `recvfrom`, `sendmsg` and `recvmsg` (with `SCM_RIGHTS`: see below), `sendmmsg`, `shutdown`, `read`/`write` on sockets, and `setsockopt`/`getsockopt` for the common options (others are accepted and ignored). Blocking follows the descriptor's `O_NONBLOCK` (`fcntl` or `ioctl(FIONBIO)`). `ppoll` and `pselect6` work across sockets, pipes and files (files are always ready). `AF_UNIX` sockets (stream, datagram and seqpacket, and `socketpair`) are the runtime's own objects, on every host (runtime/src/unix.rs): a path names a file under the root, which `bind` creates and `stat` reports as a socket (unlinking it removes the name); abstract names live in the runtime alone; `getsockname` reports the address the guest bound; `SO_PEERCRED` gives the connecting process. Descriptors passed in `SCM_RIGHTS` messages are the open file descriptions themselves, whatever they are. Only a path forwarded to a host socket (`--wayland=host`, see "Wayland") connects on the host: that socket is then a host one, and descriptors passed over it are host descriptors (a file, memfd, socket, directory or standard stream as itself; one received becomes a file, socket or directory, or anything else, a host pipe, a generic host descriptor the guest reads, writes and polls; the runtime's own objects pass to a guest process at the other end as a token it trades for the object). Other address families (`AF_NETLINK`...) return `-EAFNOSUPPORT`; glibc copes (no nscd; `getaddrinfo` assumes both IP families). Names resolve as the guest's libc does, from the root's `/etc/hosts` and `/etc/resolv.conf`; if the root's `/etc/resolv.conf` is missing or empty, as in a fresh image, the runtime provides the host's (as Docker does for containers). Writing to a broken connection returns `-EPIPE` without raising `SIGPIPE`.

**Wayland.** With `wasm-env run --wayland` (or `wasm-env shell --wayland`), graphical programs are clients of the runtime's own Wayland compositor (runtime/src/wayland/), on any host: each of their toplevels is a window of the host's (winit, drawn in software with softbuffer), on macOS, Windows or Linux alike, and needs no Wayland on the host. The environment gets `XDG_RUNTIME_DIR=/run/user/0` (created, mode 0700) and `WAYLAND_DISPLAY=wayland-0`; `/run/user/0/wayland-0` is the compositor's socket (a runtime Unix socket, see "Networking"). It offers `wl_compositor` (surfaces, regions), `wl_subcompositor`, `wl_shm` (ARGB8888 and XRGB8888 buffers, read from the files clients pass: memfds), `wl_seat` (pointer and keyboard; the keymap is a built-in US layout, passed as a memfd, so the host needs no xkbcommon), `wl_output` and `zxdg_output_manager_v1` (the host's primary display), `xdg_wm_base` (toplevels, and popups drawn into their toplevel's window), a clipboard that holds nothing (`wl_data_device_manager`), and `wp_viewporter` (accepted; not yet scaling). Frame callbacks fire at 60 Hz. `--wayland=headless` runs the same compositor with no windows (tests; also what `--wayland` falls back to when the host has no window system). `--wayland=host` instead hands the guest a Linux host's own compositor (`$WAYLAND_DISPLAY`, a name in the host's `$XDG_RUNTIME_DIR` or a path), as an optional path: connecting to `/run/user/0/wayland-0` then reaches the host socket, and buffers and descriptors pass as host descriptors. GPU buffers (`linux-dmabuf`, EGL) wait for the GPU service to render (below).

**GPU.** `/dev/wasm-env-gpu` is the runtime's GPU service (runtime/src/gpu.rs, on gpu/): the host's GPU through wgpu (Vulkan, Metal or DirectX 12), or software Vulkan with `WASM_ENV_GPU=software`, on any host; its first request fails with `ENODEV` where there's no adapter at all (the GPU opens then, for the API that asks: OpenCL's operations or Vulkan's). Each open is a session: buffers and programs made through it last until it closes. Requests are `ioctl(fd, 0xc0805740, block)` with a 128-byte block (an operation, nine arguments, six results; the operations are listed in runtime/src/gpu.rs): the device's description, buffers (create, free, read, write, copy, fill), programs built from OpenCL C (by the toolchain's clang, with OpenCL's builtins from LLVM's libclc linked in and inlined, then translated to WGSL: the build log says what a kernel uses that isn't supported; an installed wasm-env has libclc in `lib/wasm-env/clc`, `$WASM_ENV_LIBCLC` overrides, and a source tree's comes from packages/libclc/build.sh), their kernels' arguments, and kernel launches. Launches run in order; a read waits for the work before it. OpenCL programs reach it through wasm-env's OpenCL driver, an ICD for the Khronos loader (`libOpenCL.so.1`, Ubuntu's ocl-icd): `libwasm-env-opencl.so` (packages/opencl), registered in `/etc/OpenCL/vendors/`. The device is OpenCL 1.2, with images: an image is a buffer of its pixels, its header (extent, pitches, format) passed with each image argument in the argument block, and the image builtins are an OpenCL C library (gpu/src/images.cl) linked into the kernels that use them. 64-bit integers are emulated (`vec2<u32>`), and so are doubles (cl_khr_fp64), IEEE-exact in software on 32-bit integers (gpu/src/f64.rs) unless the device's own f64 behaves as OpenCL's (denormals kept, conversions not folded away; tried when it opens, `WASM_ENV_GPU_SOFT_F64` to refuse it); halves (cl_khr_fp16) are floats rounded to half precision. lavapipe runs 128 bits wide (`LP_NATIVE_VECTOR_WIDTH`): at its default 256 it miscompiles large shaders and reads textures wrongly; and for Vulkan, on x86-64 with AVX2, with llvmpipe's AVX code (`GALLIUM_OVERRIDE_CPU_CAPS=avx`): its AVX2 and AVX-512 code crashes sampling a texture at 128 bits (Mesa 26.2). Either variable, set, is kept. Programs build whole, or compile (with headers, from the environment's paths: the program's `-I` options and absolute includes resolve inside its root) and link; a program's binary is its LLVM IR (bitcode for a compiled or linked one, the IR it was built to for one built whole), which builds again without the options it was built with. Programs see the macros of the device's extensions and no others. A kernel's `printf` appends records to a buffer bound after its arguments (1 MiB); after the launch the driver formats them, a conversion at a time, with the program's own C library, and writes them to its `stdout` (`PRINTF`, in runtime/src/gpu.rs).

**Vulkan.** Vulkan programs reach the same service through wasm-env's Vulkan driver, an ICD for the Khronos loader (`libvulkan.so.1`): `libwasm-env-vulkan.so` (packages/vulkan), registered in `/usr/share/vulkan/icd.d/wasm-env_icd.aarch64.json`. Its entry points are generated from the Vulkan registry (`vk.xml`, by packages/vulkan/entries.awk): every command of Vulkan 1.0 and 1.1 and of the extensions it has, each of its own functions checked against Vulkan's type for it, and every other a stub that says once on stderr that it isn't implemented and fails (`VK_ERROR_FEATURE_NOT_PRESENT`). It is Vulkan 1.1 (with the KHR extensions 1.1 made core that it has whole, for programs written for 1.0): one queue, for graphics, compute and transfers; one memory type, device-local, host-visible and coherent; buffers; SPIR-V shader modules, which the runtime reads with naga (`VK_SHADER`); compute pipelines (`VK_PIPELINE`); descriptor sets of storage and uniform buffers; push constants (up to 128 bytes); command buffers, recorded by the driver as a stream of commands the runtime replays in order as one submission (`VK_SUBMIT`: binds, dispatches, copies, fills, updates); fences, semaphores and events. Device memory is a buffer, and a buffer is a range of one. Memory a program maps is a copy in its own memory: sent whole when it's mapped, then before each submission where the submission's commands read it (descriptors' buffers, vertex and index buffers, copies' sources, indirect draws' buffers), and as it's flushed or unmapped, each time only what differs from what the device last had from it (`VK_SEND`, compared 4 KB at a time: a game's tens of megabytes of mapped memory are mostly unchanged); and after a wait (a fence, the queue, the device) it's updated where the device may have written (copies', fills' and updates' destinations, and the storage buffers and texel buffers a draw's or dispatch's pipeline writes, which the runtime finds in its shaders: `VK_PIPELINE`'s r2), so the program's own writes elsewhere in it stay; a submission while device writes to mapped memory aren't read back yet reads them back first. In a compute shader every buffer is read-write storage, as WebGPU won't have one buffer (one memory) bound both read-only and read-write in a dispatch; in a vertex or fragment shader buffers are read-only storage unless the shader writes one (then all are read-write, as two may be ranges of one memory). Push constants are a read-only storage buffer in the last bind group, after every descriptor set the device has (so a vertex and a fragment shader, read separately, agree on it). Images are textures of their own (optimal tiling; memory bound to one is unused), with views and samplers (`VK_IMAGE`, `VK_VIEW`, `VK_SAMPLER`: clamping to a border color where the device can, wgpu's `ADDRESS_MODE_CLAMP_TO_BORDER`, else to the edge; LOD bounds below 0 are 0); a format's features are the device's for it, where it says (`VK_FORMAT`; wgpu's adapter-specific format features), else WebGPU's guarantees; a texture is viewable as its sRGB or plain counterpart (Vulkan's mutable formats, as far as WebGPU's go: a view of another format fails as it's made). Descriptors may be samplers, sampled and storage images, and combined image samplers, which naga doesn't read: the runtime splits them in the SPIR-V first (gpu/src/spirv.rs), each Vulkan binding b becoming 2b and a combined image sampler's sampler 2b + 1 (an array of them an array of images and one of samplers). Commands copy buffers to images and back (a row at a time where Vulkan's rows aren't WebGPU's 256 bytes apart), copy images, and clear them (a render pass per level and layer). Graphics: render passes and framebuffers are the driver's own; each subpass begun is a WebGPU render pass of its attachments, loading as the render pass says where it first uses one (else what's there) and storing unless where it last does the render pass says not to. Graphics pipelines are made from their state (`VK_GRAPHICS`: shaders, vertex input, topology, culling, depth bias, depth and stencil tests, blending, and the subpass's formats); a vertex shader's y is flipped by naga, Vulkan's clip space being y-down. Viewport, scissor, blend constants and stencil reference, a pipeline's own or set by commands, are kept by the command buffer and set again in each pass, WebGPU's passes starting without them; a scissor is clipped to the framebuffer. Draws (direct, indexed, indirect) set the graphics pipeline and its bind groups, vertex and index buffers each time. Presenting (VK_KHR_surface, VK_KHR_wayland_surface, VK_KHR_swapchain) is as Mesa's for its software drivers: a swapchain's images are ordinary images, and presenting one copies it into a shared-memory buffer (wl_shm, BGRA; an RGBA swapchain's image drawn into a BGRA one first) committed to the program's `wl_surface`, through the program's own libwayland-client on an event queue of the driver's; FIFO, the next frame waiting for the compositor's frame callback and the buffer's release. So it works with the runtime's compositor and with a host's (`--wayland=host`); `vkcube` runs. Writes of `gl_PointSize` are dropped in the SPIR-V (WGSL hasn't it; WebGPU's points are one pixel). Specialization constants are WGSL's overrides (naga reads `OpSpecConstant` with a `SpecId` as one), each value read as its constant's type. A secondary command buffer that continues a render pass records as one inside it; the runtime keeps scissors within the pass's attachments. Blits are copies where nothing is scaled, else a quad drawn sampling the source (or fetching its nearest texels, where its format isn't filtered: integers), a 3D destination a slice at a time, each the source's slice at its middle (a transfer source is made sampleable where its format allows). A copy's extent is whole blocks (a compressed level smaller than a block). Input attachments are 2D images in the SPIR-V (naga reads no `subpassInput`), each `subpassLoad` a fetch at the fragment's position plus its offset; a render pass keeps an attachment it reads in a later subpass. Texel buffers are 2D images in the SPIR-V (a `samplerBuffer`'s sampler dropped, its fetches given level 0, texel i at (i mod 4096, i / 4096), its size the width times the height) and 2D textures of their views' texels, 4096 a row, in the runtime (`VK_BUFFER_VIEW`), copied from their buffers before each pass or dispatch that may read them: as many texels as 4096 rows of a 2D texture's width (a 1D texture would hold fewer than Vulkan's 65536). Shaders reach wgpu as naga's IR, not WGSL, whose structs can't say the SPIR-V's explicit layout (std140's arrays of scalars 16 bytes apart, offsets of its own); matrices WGSL can't lay out (std140's `mat2`, `mat3x2` and `mat4x2`, columns 16 bytes apart, and row-major ones) are arrays of their columns or rows in the SPIR-V, made matrices as they're loaded and arrays as they're stored, a row-major column a component at a time (gpu/src/spirv/matrices.rs). A buffer bound for a block WebGPU rounds up (a `bvec3`'s 12 bytes to 16) is bound as big as the block, where its memory has room (a buffer's memory is a multiple of 16 bytes). Memory decorated coherent or volatile is plain. A stage's inputs and outputs that are arrays, matrices or structs (interface blocks among them) are private variables in the SPIR-V, each scalar or vector an input or output of its own at the locations they took, copied in as the entry point begins and out as it returns (gpu/src/spirv/interface.rs); a fragment shader's color outputs of fewer than four components are four (WebGPU wants as many as the attachment's format has), `gl_SampleMask` a u32, and a sample of an integer 2D image (WGSL samples none) a fetch at the coordinates times its size. Shaders and pipelines that fail as wgpu makes them (validation, a backend's shader that won't compile, out of memory) fail as Vulkan's calls, and a submission the runtime can't replay (a panic among them) as the device lost; `WASM_ENV_DEBUG_GPU` shows wgpu's warnings and `WASM_ENV_DEBUG_WGSL` each shader as WGSL. A work group sized by specialization constants (`local_size_x_id`, `gl_WorkGroupSize`) is sized in the SPIR-V for each pipeline's values. A texture that's only fetched from is bound as unfilterable (a float one may not filter). Descriptor arrays are binding arrays, where the device has them (requested for Vulkan; naga, vendored, had taken a fetch from an array's element for one from the array): each element bound, its index above the kind's byte. An array of blocks (a descriptor array of buffers) is a binding array of buffers. Graphics pipelines, and those with binding arrays, have layouts of their own reflected from their shaders (wgpu's derived ones are of single items, and refuse a binding two stages declare differently). A shader computing with specialization constants (`OpSpecConstantOp`, which naga doesn't read) is specialized in the SPIR-V for each pipeline's values, its expressions evaluated. `isnan` and `isinf` test the bits. Buffers copy at any offset and size (a compute shader copies the bytes WebGPU's word copies can't); 32-bit float attachments blend where the device can; a depth-only view of a depth and stencil image is attached through a view of both. Images of four samples, as WebGPU has them (2D attachments of formats it multisamples: `VK_FORMAT`'s r3); 1D images are 2D textures a row high, and the shaders' 1D images 2D (gpu/src/spirv/images1d.rs: coordinates given a y of 0.5 sampled or 0 fetched, sizes the width), so they have levels, layers and attachments as Vulkan's do (WebGPU's 1D textures have none); 3D images are neither depth nor blocks; an image that isn't an attachment is cleared by a copy of the color packed (RGB9E5's too), a 3D one a slice at a time, a linear one by its memory filled (`FILL_TEXELS`); copies between formats of texels the same size go through a buffer (WebGPU copies between one format's only); linear images (VK_IMAGE_TILING_LINEAR: one level and layer, color formats of whole bytes, copies only) are the memory bound to them, their rows one after another (`vkGetImageSubresourceLayout`), so copies to and from them are copies to and from that memory, as programs that read results back through a host-visible image do; 24-bit depth (which WebGPU won't copy) is read into buffers by a compute shader and written from them by a draw of its values, and stencil rows that aren't whole words a byte at a time; a subpass's resolve attachments are its WebGPU pass's resolve targets, and `vkCmdResolveImage` a pass that keeps the source and resolves it (whole levels and layers). `vkCmdClearDepthStencilImage` is a render pass that clears; `vkCmdClearAttachments`, inside one, a quad over each rectangle (its samples taken off an occlusion query's count, as Vulkan's clears aren't counted), drawn by a pipeline made for the pass's targets that writes the clear values to the attachments named and nothing to the others. Queries (`VK_QUERY_POOL`): occlusion, inside render passes (a pass's pool named as it begins), and timestamps, where the device takes them anywhere in a submission (their period in `VK_LIMITS`); a submission resolves the queries it ends and reads them back once it's done, so `vkGetQueryPoolResults` (`VK_QUERY_RESULTS`) has them, and `vkCmdCopyQueryPoolResults` copies them as they are. A graphics pipeline used in a render pass whose color formats aren't its own (made for RGBA, drawing into BGRA: Vulkan's drivers let it, vkQuake 1.36.0 does it) draws through a variant made for the pass's formats. Depth and stencil images are copied to and from buffers whole, through a buffer of WebGPU's pitch. The optional features it has are reported, and asked for are accepted: those every device has through it (robust buffer access, 32-bit indices, cube arrays, independent blends, multiple indirect draws, depth bias clamps, anisotropic filtering, fragment shaders' stores) and those the device has (descriptor arrays indexed dynamically, 64-bit floats and integers, indirect draws' first instance, BC compression: BC1 to BC7 images, copied a row of blocks at a time). Triangle fans are lists: a draw's indices made in the replay, an indexed draw's by a compute shader before its render pass (indirect fans aren't). Depth bias and stencil masks left to commands are a pipeline's variants, made for the values set, and so is an indexed draw's index format where the topology is a strip (WebGPU's pipeline names it). A vertex attribute past its binding's stride (Vulkan's may be; WebGPU's may not) is in a vertex buffer slot of its own, the binding's buffer from its offset. Formats report what they are as vertex attributes and texel buffers (`bufferFeatures`). A stencil test on a format without stencil is dropped (Vulkan ignores it; WebGPU refuses it). A pipeline barrier inside a render pass (a subpass reading what it drew) ends the WebGPU pass there and begins another that loads what the first stored. A multisampled view of one layer of an array is a 2D view. Cube storage images (WGSL has none) are 2D arrays of their layers in the SPIR-V (gpu/src/spirv.rs, `cube_storage`: their coordinates are a 2D array's already, a cube array's size its layers / 6), bound as a 2D array view of the cube's. A block's vector at an offset WGSL's alignment doesn't allow (relaxed block layout) is an array of its components in the SPIR-V, made a vector as it's loaded. naga (vendored) rounds a sampled array's float layer, as SPIR-V does, rather than truncating it. A subpass that reads an attachment it draws into (an input attachment with a self-dependency) reads a copy of it made as its pass begins. A render area smaller than the framebuffer clears with a quad over it, the attachments loaded. Storage texel buffers are written back to their buffers after each dispatch and pass. An occlusion query begun outside render passes counts in each pass begun while it's on (a slot of an overflow set of the pool's), summed. Vulkan 1.1: its structures in the `...2` queries' chains (multiview its one optional feature, as 1.1 requires; not 16-bit storage, protected memory, YCbCr conversion, draw parameters or variable pointers), memory requirements and binds of `...2`, descriptor update templates, one device group of the one device, no memory, fences or semaphores shared outside, and maintenance1's negative viewport heights (a pipeline variant whose vertex shader isn't flipped, the viewport made positive) and pipelines culling both faces (their triangles not drawn). Subgroups are of one invocation on any device, made so in the SPIR-V (gpu/src/spirv/subgroups.rs: basic and vote operations; `gl_HelperInvocation` false). Multiview: a subpass with views is drawn again for each, into its layer of each attachment (a load op applying where a view first uses an attachment; queries one a view), `gl_ViewIndex` a word bound beside the push constants (binding 1), an input attachment's layers read at the view's. `vkCmdDispatchBase` dispatches from work group 0 only. Events a command buffer sets or resets are set or reset as it's submitted. An extension's commands are found only where it's enabled. A framebuffer of several layers (not multiview) is drawn through its first layer (what draws reach without geometry shaders), a load op that clears clearing every layer and `vkCmdClearAttachments` of later layers done after the pass, a layer at a time. A subpass of no attachments (its fragment shaders' side effects all it does) draws into a dummy attachment of the framebuffer's size that's never kept, its pipelines given a target nothing's written to. Not yet: other window systems (X11), other line widths, pipeline statistics, sparse binding, and the device's optional features beyond those; subgroups of more than one invocation; multisampled 2D arrays of more than one layer (WebGPU's have one); unnormalized sampler coordinates; binding numbers above 499 (WebGPU's are below 1000, a binding b being 2b and 2b + 1); anisotropy where a filter isn't linear; packed 16-bit formats; image atomics (naga reads none from SPIR-V); views' component swizzles; vertex strides that aren't multiples of 4; indirect draws of triangle fans;  a vertex shader's interpolation differing from the fragment shader's; block-compressed images of sizes that aren't whole blocks; and blocks whose members' offsets aren't in order. tests/vulkan-cts.sh runs Khronos's conformance tests (VK-GL-CTS, built for arm64) against it.

**Audio.** `/dev/snd` is the runtime's sound card (runtime/src/audio.rs), speaking ALSA's kernel interface so the environment's own `libasound` (and SDL, everything over ALSA) works unmodified: `controlC0` (the card, its driver "wasm-env": no card configuration of `libasound`'s matches it, so `default` is `plug` over `hw`, conversions the card lacks done in the guest) `pcmC0D0p`, playback, and `pcmC0D0c`, capture, character devices of major 116. The card's controls are a master volume (two channels, 0 to 100 in half-decibel steps from -50 dB, its dB scale readable as a TLV, 0 silent) and a master switch, which `amixer` and `alsamixer` show as "Master"; the mixer applies them to what it plays. They last as long as the runtime. A PCM takes U8, S16_LE, S32_LE and FLOAT_LE, one or two channels, 8 to 192 kHz, buffers of 80 ms or more (a translated program needs the slack, and a host's output may take 20 ms at a time), and the kernel's rules between its parameters (`HW_REFINE`: the same interval arithmetic, so `libasound`'s negotiation finds what Linux would). Frames arrive by `WRITEI_FRAMES` and `WRITEN_FRAMES`, or, with memory-mapped access, in memory of the program's own that mapping the PCM gives it, copied in when `SYNC_PTR` moves the application pointer (`libasound`'s conversion plugins write that way); the status and control pages aren't mapped, so `libasound` uses `SYNC_PTR`. A stream's frames wait in a ring buffer which the mixer drains: every running stream, converted to float stereo at the output's rate (resampled linearly), summed. Starting with nothing written fails with `EPIPE`, as Linux's does (SDL starts its device before writing); a stream that runs out underruns at its stop threshold. The output is the host's (`cpal`: CoreAudio, WASAPI or ALSA), or none (`--audio=null`: the mixer on a clock of its own), which can record what each stream played, as written (`WASM_ENV_AUDIO_RECORD`, for tests). Capture streams are the same the other way round: the hardware pointer advances as frames are captured into the ring (from the host's default input, resampled, or silence where there's none or with `--audio=null`), the program's as it reads them (`READI_FRAMES`, `READN_FRAMES`, or from its mapping, copied out at `SYNC_PTR`), overrunning at the stop threshold; reading starts a prepared stream. For tests, `WASM_ENV_AUDIO_SOURCE` names a file whose bytes a capture stream captures as its frames, then silence. Programs that speak PulseAudio's protocol (through the environment's own `libpulse`: GStreamer, SDL, browsers) are clients of the runtime's own PulseAudio server (runtime/src/pulse/), as Wayland programs are of its compositor: on `/run/pulse/native` (libpulse's system-wide socket, which it tries after the user's: no setup needed) and `/run/user/0/pulse/native`. It speaks protocol version 35 without shared memory (audio inline in the connection's frames). Its one sink (`wasm-env-output`) and one source (`wasm-env-input`) are the card: each stream a client makes is one of the card's (in the client's own format where the card takes it, else converted to float stereo, mixed down by channel position, and back for capture), mixed with ALSA programs' streams; the sink's volume and mute are the card's master volume and switch. Streams follow PulseAudio's buffering: the client is asked for what's been played (`REQUEST`, in batches of at least `minreq`), playback waits for `prebuf` bytes and, after an underrun, for them again, or, without prebuffering, runs on through silence (the clock a program derives from the read position goes on); drains are answered when what was written has played. One card, no modules, cards, sample cache or moving between devices; each run of the runtime starts at full volume.

**fork (translated programs).** A translated program's state at a syscall is all in its memory: the guest registers are in the thread's guest-state block, and nothing on the host stack matters (the lifted code reaches the syscall through tail calls). So `clone` without `CLONE_VM` or `CLONE_THREAD` makes the child a copy: a new process whose memory holds the parent's pages (those in use: the image, break and mmap region, and libraries; untouched pages stay unallocated), with copies of the descriptor table, working directory, credentials and signal dispositions, running new instances of the program and its libraries with the same placements. The support code passes a clone frame (see "Threads"); the runtime points the child's instance at the forking thread's thread-local block and C stack (`__tls_base`, `__stack_pointer`, both exported) and calls `__wasm_env_fork_start(frame)`, which resumes after the `clone` with x0 = 0. `CLONE_PARENT_SETTID`, `CLONE_CHILD_SETTID` and `CLONE_CHILD_CLEARTID` apply. Only the forking thread exists in the child, as on Linux. A fork takes a few milliseconds.

**Credentials.** A process has user and group ids (real, effective, saved) and supplementary groups, starting as root; the `set*id`, `get*id`, `setgroups` and `getgroups` calls change and report them, and they pass through fork, vfork and exec. They are only numbers: files belong to the host user, and permissions aren't checked.

**Terminals.** When the runtime's stdin, stdout or stderr is a terminal, `TCGETS`, `TCSETS*`, `TIOCGWINSZ`, `TCXONC` and `TCFLSH` on them go to the host terminal (on Linux hosts: the structures have the same layout), and `TIOCGPGRP`/`TIOCSPGRP` read and set the environment's foreground process group. Ctrl-C and Ctrl-\ at the host terminal send SIGINT and SIGQUIT to that group; the terminal's settings are restored when wasm-env exits.

**Locks.** `fcntl`'s record locks (`F_GETLK`, `F_SETLK`, `F_SETLKW` and the `F_OFD_` forms) and `flock` are the runtime's, on every host (runtime/src/locks.rs): a table keyed by the host file's identity, as Linux's kernel keeps it, since the environment's processes share one host process and the host's per-process locks would never conflict between them. A process's record locks go when it closes any descriptor for the file, or exits; an open file description's (`F_OFD_`, `flock`) with its last descriptor; record locks and `flock` locks don't see each other. Locks are between the environment's processes: host programs outside it don't see them.

**fork (programs built with the toolchain)**, which keep C state on the host stack, remains open (they have vfork). The options:

| Option | How it works | Trade-off |
|---|---|---|
| Asyncify-style unwinding | The compiler instruments code so the call stack can be saved to memory and rebuilt in a copy of the process | Works on any runtime; code grows and slows (roughly 10–50%) |
| Stack switching | Use the WebAssembly stack-switching proposal to capture the running stack | Cheap, but the proposal isn't finished and wasmtime support is experimental |
| Runtime-level snapshot | wasmtime copies the instance, including its native stack | No compiler changes; needs deep wasmtime changes |
**Environments.** `wasm-env convert IMAGE DIR` turns an arm64 Linux image (an OCI reference pulled from its registry, an OCI layout, or a root filesystem tarball or directory) into an environment: its root filesystem, with every arm64 program and library translated into `/var/cache/wasm-env` inside it (`--lazy`: on first use instead). Translations are keyed by content and by the translator's version, and libraries in the image are registered by their path in it, so an environment can move. `wasm-env shell DIR` runs a login shell in it; `wasm-env export DIR OUT[.tar]` writes it as an OCI image layout for platform wasi/wasm (one layer, translations included). An environment's symlinks are the host's on Unix hosts; on Windows, where making one needs privileges, they are link files (a small file with the System attribute holding a marker and the target), which the runtime, `convert` and `export` all treat as symlinks, so an environment for Windows is made on Windows. Translating needs a toolchain (clang, wasm-ld, compiler-rt builtins for wasm64): an installed wasm-env has one in `lib/wasm-env/toolchain` next to its binaries (`$WASM_ENV_TOOLCHAIN` overrides), and the dev shell provides it through `$WASM_CC`.


## Toolchain

- Target: `clang --target=wasm64-unknown-unknown`, wrapped by `wasm64-linux-musl-cc`, which sets the sysroot and flags and defines `__linux__` and `__unix__` (but not `__gnu_linux__`, since this is musl). clang has no `wasm64-*-linux` target, so the wrapper stands in for one.
- `long double` is 128-bit IEEE quad, as on arm64 Linux, emulated in software (compiler-rt builtins).
- Linking is static: `crt1.o`, the program, `libc.a` and compiler-rt builtins, linked by `wasm-ld`. Dynamic linking is out of scope.

## Planned versions

- **Version 1: dynamic linking** (PLAN.md, M3). Several modules in one process, sharing one memory and one function table, loaded and linked by the runtime at run time, including `dlopen`. Needed so translated programs can load shared libraries such as Python extension modules. Translated modules use glibc's symbol versions. (Translated programs already have them; see "Libraries".)
- **Version 2: threads** (PLAN.md, M6). Shared memory, atomics and `clone(CLONE_THREAD)`, with real thread-local storage, for programs built with the toolchain. (Translated programs already have them; see "Threads".)

## wasm-env's own calls

Syscall numbers from 2^32 up are wasm-env's, not Linux's; unknown ones return `-ENOSYS` like any other.

| Number | Call | Arguments |
|---|---|---|
| 2^32 | `missed_target` | (address, object name, offset in the object). Made by a translated program's support code when it jumps to code the translation missed and `translate_code` can't translate it then (see "Blocks a translation missed"). The runtime records the address, and the next translation of that program includes it. |
| 2^32 + 1 | `thread_started` | (). Made by a new thread of a translated program once it has taken its registers from its clone frame (see "Threads"). |
| 2^32 + 2 | `load_library` | (fd, range). Made by a translated program's support code when the dynamic linker maps a file: loads it as a library module if it is one, writing its guest start and end at `range` (see "Libraries"); else `-ENOEXEC`. |
| 2^32 + 3 | `sync_modules` | (). Made when a thread reaches a library module its instance hasn't loaded yet (see "Libraries"). |
| 2^32 + 4 | `translate_code` | (address, object name, object base). Made when control reaches an address no translated block covers: for code the program generated, translates the executable memory holding it (see "Code generated at run time"); for a block the program's or a library's translation missed, translates its page again (see "Blocks a translation missed"; the object is the program's, or zero for a library module). 0 if it translated something, 1 if the address was translated already (the thread's dispatch cache named older code), `-ENOEXEC` if it can't. |
| 2^32 + 5 | `code_changed` | (start, length). Made at an `isb` after `ic ivau` (instruction cache maintenance, after writing code): translations of code in that range whose bytes changed are retired (see "Code generated at run time"). |
| 2^32 + 6 | `exact_fp` | (address, object name, object base, as for `translate_code`). Made when code with FP results enters a region while FPCR sets a rounding mode, flush to zero or default NaNs, which translations don't follow: translates the address's page again with every FP result as FPCR says (`--exact-fp`) and adds it to the module directory with the top bit of its generation set, so `dispatch` passes over it and only the support code's `__wasm_env_exact_fp` uses it. A page translated again for a missed block retires its exact version. 0 if it translated it, 1 if it was there already, `-ENOEXEC` if it can't. |

## Versioning

The module declares the ABI version it was built for in a custom section named `wasm-env.abi`, containing the version number as a LEB128 integer. Version 0 is this document. The runtime refuses versions it doesn't know.
